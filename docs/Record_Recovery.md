# Quick routine edits and record recovery

Ordinary inline Save/Delete performs one bounded private recovery write and one guarded D1 transaction. It saves the affected shape, optional physical inventory row, tags and associations as before/expected-after states; it neither scans storage nor copies originals. Existing shape identities/files, BIN policy and OneNote provenance are preserved. Full snapshots remain for backup, bulk import and whole-catalog restore.

Recovery records use the existing private R2 bucket under `catalog-backups/record-changes/`, checksum protected and capped at 256 KiB. Their newest-first keys allow a ten-item listing without scanning history. Saving a recovery record is required before mutation; storage failure blocks the save and retains the draft. A stored record is an attempted change, not a standalone commit receipt. Full current-state matching determines whether undo is applicable, and prepared/failed attempts are not reported as committed changes. No schema migration or new storage resource is introduced. Records are retained without automatic pruning; retention/reclamation remains follow-up work.

Owner/admin opens Undo recent record changes, selects Review change, reviews each changed field in the Current / After undo table, and explicitly approves Undo this change. Preview and apply require owner authorization; apply also requires same-origin headers, approval and the reviewed revision. Restore guards recheck the exact affected rows and tags inside one D1 transaction. New relationships block record removal. Shared tags and originals are preserved; changed shared tag definitions cannot be silently overwritten. Each undo saves an inverse recovery record before applying, so an undo can itself be reviewed and reversed. Invalid/corrupt recovery records fail. Fifty-tag restoration uses bounded bulk SQL rather than one query per association.

The JSON before/after records include source metadata and remain private. They are outside normal live-original audits and portable whole-catalog archives. The whole-catalog restore retains this private namespace; record undo may become unavailable if the catalog no longer matches the recorded result. An independent off-provider copy and whole-catalog disaster recovery remain separate requirements. This implementation adds no automatic backup pruning or daily schedule activation.

Compatibility: the old inline checkpoint endpoint remains temporarily for already-open older clients. Refresh the app to use the new one-request Save/Delete interface. Bulk import, whole-catalog restore and legacy archive/helper formats are unchanged. Broader advanced catalog forms have their existing revision safeguards; this record recovery path covers the inline shape/physical workspace only.

Validation: 135 application tests and build/type-check. Tests reject any original-file/storage enumeration by routine changes, verify one small recovery write, round-trip edit/delete/create undo, preserve original source/tag values, reject unavailable/corrupt recovery records and non-owners, keep drafts after conflicts, and roll back failed/racing SQL including undo. Live development 3734795 passed create/edit/delete/undo acceptance; individual observed actions were around one second, with no original scan or full backup loop. Disposable rows were cleaned up.
