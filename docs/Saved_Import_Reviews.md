# Saved source reviews and import previews

This is development implementation for CC-TODO-007/008/009. It preserves source-review work across tabs/sessions. It does **not** import the catalog, upload originals, populate the existing catalog review queue, or implement a live bulk importer.

## User workflow

1. Open Import preparation workspace and choose a prepared manifest. Classify items, split source pages when needed, and keep unknown details unknown.
2. Save new review. After this succeeds, List saved reviews / Open saved review can reopen it in another signed-in session. Download reviewed manifest remains an independent portable copy.
3. Record ownership and print status separately. Physical quantity is blank until known; it never silently becomes one. Slot is optional. A notebook section is not proof of current physical location.
4. Enter reference size as the longest edge in inches; it is stored internally in mm. Preserve the original size label and oriented width/height separately. Packaging and assembled dimensions do not become individual cutter measurements.
5. Save review changes, then Record import preview. Previews record classification/gap counts and ownership/quantity conflicts against a specific saved version. They do not check source bytes, infer component counts, merge duplicates, map records or apply inventory changes.
6. Saved versions and preview history can reopen an earlier version as a draft. Saving that draft creates a new version; previous versions remain. A historical draft must be saved before a new preview is recorded.

Changing item type resets ownership/quantity assertions and completion states, retaining applicable source-review notes. Describing another item from a page clears its facts/assertions and file-purpose classifications, keeping its original source reference. Confirm each resulting item's actual type/ownership separately.

Unsaved browser changes still need an explicit Save or Download. A stale save is rejected; the browser draft remains for comparison. A failed network save does not silently reload over the draft. Editors/admins may read and save source reviews; viewers cannot access the source-review API or controls. Existing catalog viewer access is unchanged.

## Storage and API

Migration 0003_import_reviews.sql adds four tables without altering the existing catalog tables: workspaces, immutable version headers, per-version item snapshots, and preview runs. The manifest retains its namespace, item source keys, page/file references, facts, catalog assertions, file descriptors and review evidence. Version headers record the verified actor subject privately. No account emails or source payload belongs in GitHub.

`/api/import-reviews` supports listing and new saves; `/api/import-reviews/{id}` supports reopen and conditional saves; `/api/import-reviews/{id}/preview` records a metadata preview. All require verified editor/owner membership; mutations also require same-origin and the import-review request marker. PUT requires the opened revision. An atomic D1 batch updates the workspace and inserts its complete version/items only when the expected revision and namespace match. Old versions are immutable through the API. Source namespace changes require a separate workspace.

Creation IDs are generated by the browser and retained for retry. An identical retry reuses the saved review; conflicting content with the same creation ID is rejected. Server checksums verify reconstructed manifests. Referenced source files remain separate, private originals; saving paths and hashes does not upload or verify their bytes.

Conservative limits: one MiB request, 1000 items per workspace version, 32000 UTF-8 bytes per item. Items are separate bounded rows so generated offline restore SQL stays below D1's statement limit. Snapshots use three write statements with JSON row expansion, rather than one statement per item. The supplied 343-entry manifest is about 434 KB compact, with a largest item around 2.2 KB, and fits these limits. List pages contain 20 workspaces. Reopen returns 50 recent version headers and 20 recent previews; older history is retained in backups. No automatic pruning is added. Existing backup row/manifest bounds still apply as history grows; exports fail explicitly at their limits.

## Backup compatibility and activation

Both legacy 16-table and new 20-table databases are supported by the updated app exporter, Node backup helper, Python TAR/JSON restore tools and isolated D1 preparation/comparison. Exact known table profiles are required; partial/unknown profiles fail safely. The TAR/JSON envelope remains version 1; schema/profile and matching migrations distinguish the contents. Older tools reject an unfamiliar table set, rather than dropping the new review data. Upgrade the helper before relying on backups of a migrated database.

The helper's schema authorizer allows only the two pure built-ins needed by bounded JSON constraints (json_valid and length). File access, extensions, arbitrary functions and previously denied schema actions remain denied; an arbitrary-function schema fails its negative test.

Activation order on the existing development database:

1. Publish the tested app/helper code. Before migration, the app still exports the existing 16-table database normally. Saved-review requests explain unavailability while the migration is absent.
2. Download a fresh complete TAR using the existing app archive control. Use the updated helper to save it as a protected pre-change backup in the existing private backup folder.
3. Apply database/migrations/0003_import_reviews.sql to the existing development database through the normal migration mechanism. If the owner uses the D1 dashboard, use [the idempotent activation SQL](../tools/Activate-Saved-Reviews.sql), including its matching d1_migrations row. Do not run against the separate recovery database or production.
4. Verify development infrastructure: 20 tables, three migrations, zero foreign-key violations, and saved review storage ready. The check remains compatible with 16 tables before activation, while reporting review storage not activated. Partial profiles or missing migration metadata fail verification.
5. Open the prepared 10-example manifest, Save new review, reopen it, and record a preview. Unknown ownership/quantity remain questions, not imported facts.
6. Download and locally validate a post-activation archive with the updated helper; it must retain all 20 tables and the saved review/history. Then continue to the actual importer and representative catalog acceptance.

This workspace has no authenticated Cloudflare migration access; owner-mediated activation and real-browser acceptance remain necessary. No remote migration, live source-review upload or inventory import is claimed by local tests.
